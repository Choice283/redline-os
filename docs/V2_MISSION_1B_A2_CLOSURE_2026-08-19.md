## Parent mission identity and scope

(`docs/V2_MISSION_1B_A1_CLOSURE_2026-08-17.md`) as the separate,

## Original parent acceptance criteria and evidence

The accepted Mission 1B-A2 architecture required the following capability
chain. Every item below is now implemented, published, and exercised by
passing tests at the exact published HEAD:

1. **Classify DB/config source condition** (`HEALTHY`/`DEGRADED`/`MISSING`)
   — Mission 1B-A2-1, `classify_database_source()`/`classify_config_source()`.
2. **Read-only recovery feasibility/planning** — Mission 1B-A2-1,
   `redline backup restore-recovery-plan <backup_id>` /
   `build_recovery_plan()` (`NOT_APPLICABLE`/`RECOVERABLE`/`RECOVERY_BLOCKED`).
3. **Preserve degraded-source evidence before destructive recovery** —
   Mission 1B-A2-2, `build_degraded_source_capture()`, a structurally
   distinct `dsc1-...` / `degraded_source_captures/` namespace.
4. **Prove safe Windows move-aside disposition behavior** — Mission
   1B-A2-3-Prep, direct behavioral proof against real `os.rename()`
   semantics for both directory-occupied and file-occupied target paths.
5. **One authoritative sidecar safety classifier** — Mission
   1B-A2-3-Prep2, `sidecar_classification.classify_sidecars()`, shared by
   both A2-1 planning and A2-2 capture.
6. **Execute destructive degraded/missing-source recovery under explicit,
   non-interactive authorization** — Mission 1B-A2-3,
   `redline backup restore-recovery <backup_id>` gated by
   `RecoveryAuthorization` (repeated `--confirm-backup-id` plus five
   itemized attestation flags; no blanket `--yes`).
7. **Mandatory same-attempt fresh degraded-source capture** — every
   `execute_recovery()` attempt calls `build_degraded_source_capture()`
   unconditionally; no `--capture-id`/`--confirm-capture-id` exists
   anywhere in the signature or CLI parser.
8. **Capture reverification** — the fresh capture is reverified against
   the exact same `capture_id` before proceeding.
9. **Fresh source/sidecar reclassification** — reclassification is
   re-performed post-capture, independent of the pre-capture recovery
   plan's own classification.
10. **Pre-mutation stability binding** (`PRE_MUTATION_STABILITY`) — a
    fingerprint-based stability check gates entry into disposition.
11. **Mutation-bound target revalidation** — a stability recheck runs
    immediately before each individual disposition move and each
    replacement step, not once for the whole attempt.
12. **Collision-refusing disposition** — `recovery_disposition.py`'s
    move-aside contract, proven against real Windows behavior by
    1B-A2-3-Prep, never overwrites an existing destination.
13. **Final pre-replacement stability** (`FINAL_STABILITY`) — a last
    stability gate immediately before staging/replacement begins.
14. **Shared Restore verification authority** —
    `RestoreManager._verify_restore()`'s exact STEP 0–6 body was extracted
    into module-level `verification.verify_restore()`; ordinary Restore
    and A2-3 recovery call the identical implementation.
15. **Append-only journal/evidence trail** — `RestoreJournal` gained an
    opt-in `attempt_kind="recovery"` parameter (ordinary Restore's payload
    shape unchanged) and 23 additive `RestoreState` members (27 → 50,
    zero removed, zero renamed).
16. **Fail-closed doctrine** — no automatic retry, rollback, resume,
    delete fallback, or overwrite fallback exists anywhere in the A2-3
    code path; every failure mode raises a typed exception and stops,
    with already-completed mutations left journaled and preserved for
    manual inspection.
17. **Published exact-head CI success** — run `32260711193`, `headSha`
    `d240ddbbc6ba3bb52a79884eccc6e2c5c1905d24`, `conclusion: success`.

**All seventeen accepted parent Mission 1B-A2 implementation capabilities
are complete.**

## Architecture and safety summary

The implemented execution safety chain (Mission 1B-A2-3,
`docs/BACKUP_RECOVERY_ARCHITECTURE.md` §16):

```
RecoveryAuthorization
  -> fresh recovery-plan validation
  -> mandatory fresh degraded-source capture
  -> capture reverification (exact same capture_id)
  -> CHANGED_DURING_CAPTURE hard-stop check
  -> fresh source/sidecar reclassification
  -> PRE_MUTATION_STABILITY
  -> quiescence (proved probe, or not-applicable)
  -> mutation-bound disposition stability check (immediately before each rename)
  -> disposition (fixed order: database -> config -> -journal -> -wal -> -shm)
  -> FINAL_STABILITY
  -> existing sidecar pre-check (reused, unmodified)
  -> mutation-bound DB/config stability checks (immediately before each replacement step)
  -> staging/replacement (reused, unmodified)
  -> shared Restore verification (verify_restore(), STEP 0-6)
  -> terminal journal state
```

`RECOVERY_BLOCKED` is absolutely non-overridable — checked at both initial
recovery-plan validation (before any capture) and fresh post-capture
reclassification, with no field on `RecoveryAuthorization` and no CLI flag
anywhere in this repository able to bypass it. Mission 1A (backup),
Mission 1B-A1 (restore), and Mission 1B-A2-1's own read-only planning
remain locked, unmodified foundations throughout the entire Mission 1B-A2
family — verified by zero-diff checks recorded in each child closure.
