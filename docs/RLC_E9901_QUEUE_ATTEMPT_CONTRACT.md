## 1. Purpose

This harness prepares, but does not perform, the first live RLC-E9901 Broadcast Master production `render queue` attempt. It answers a narrower question than the preflight tooling: given that the getter-only preflight already passed once (preserved evidence, §4), can Redline OS's own, already-tested, unmodified production code (`RenderManager.queue_render()` via `python -m cli.main render queue RLC-E9901 broadcast_master`) be launched exactly once, under a fail-closed contract that proves its source, environment, and preconditions match what was reviewed, obtains one fresh getter-only guard immediately beforehand, and preserves complete, honest evidence of whatever actually happens — success, a clean failure, or a state requiring manual reconciliation?

It does not decide whether Paul should authorize a live attempt. It does not implement any new Resolve-mutating logic: the only mutation-capable code is the real production `RenderManager`/`ResolveAdapter` pathway, running exactly as committed, launched as an opaque external process.

## 5. Fresh pre-queue getter-only guard

Immediately before the production CLI launches, the harness subprocess-launches the already-published, already-reviewed Rev5 preflight wrapper's own `run-live-preflight` subcommand:

```
<python> scripts/rlc_e9901_snapshot_preflight_contract.py run-live-preflight --authorized-commit <commit> --output <evidence_dir>/fresh_preflight/RLC-E9901_queue_attempt_fresh_preflight_<commit[:7]>.json
```

This is a **fresh, independent path** inside this attempt's own evidence directory — never the historical preflight path, which is only ever read. The wrapper's own internal gates (repository checkpoint, collector/checker hash pinning, Python interpreter, evidence-path safety) all re-run as part of this call. The harness requires `render_preflight_status == "passed"` from this fresh result before proceeding; any other outcome stops before the production CLI is ever launched. Reusing this already-reviewed tool avoids introducing a second, independent direct-Resolve-API safety surface.

Before this subprocess can even launch, `prepare_fresh_preflight_evidence_subdirectory()` creates exactly `<evidence_dir>/fresh_preflight` and nothing else (**Rev2 Finding 1**). The published wrapper's own `--output` path validation fails closed with `evidence_parent_directory_missing` unless the file's immediate parent directory already exists — it never auto-creates one — and the harness's constructed output path is one directory level deeper than the evidence root itself. `test_real_published_preflight_validator_accepts_the_prepared_parent` proves this using the real published wrapper's own validator function, not a fake subprocess that merely returns PASS.

**Rev3 Finding R3-3 — binary capture.** Both live-capable subprocess launches (this one and the production CLI, §6) use `subprocess.run(..., capture_output=True)` with no `text=True`. With `text=True`, Python decodes the pipe *inside* `subprocess.run()` itself, and an undecodable byte can raise `UnicodeDecodeError` before this harness's own lossless `CapturedOutput` abstraction (base64 fallback for non-UTF-8 bytes) ever sees anything — an independent replay reproduced exactly this. Binary capture makes `.stdout`/`.stderr` (on both a completed process and a `TimeoutExpired`) raw `bytes` unconditionally, which `_normalize_captured_output()` already handles losslessly.

**Rev6 Finding 1 — fresh preflight wrapper stderr.** A fresh preflight result may be treated as PASS only if ALL of: exit code 0; `render_preflight_status == "passed"`; **and the wrapper process's own raw stderr stream is exactly zero bytes**. This is the wrapper subprocess's own stderr, never the `collector_stderr` field embedded inside the wrapper's own JSON stdout result (that field is the wrapper's own already-reviewed evidence of its internal collector subprocess — a separate, already-handled concern). Any non-empty wrapper-process stderr — including non-UTF-8 bytes — stops (`fresh_preflight_stderr_nonempty`) before the snapshot-binding check, before the mutation-boundary recheck, and before production launch, while preserving the raw fresh stdout/stderr evidence exactly as captured.

### 5a. Fresh snapshot binding (Rev2 Finding 5; hardened Rev3 Finding R3-4; metadata made mandatory Rev6)

A reported `render_preflight_status == "passed"` is not, by itself, sufficient — `verify_fresh_preflight_snapshot_binding()` additionally requires the fresh preflight's own output file to exist, computes its SHA-256 independently, and requires an exact match against the wrapper's own printed JSON result's `snapshot_path`/`snapshot_sha256`. Any mismatch or missing file stops before the mutation-boundary recheck or production launch. This binds the queue-attempt evidence chain explicitly: historical preflight SHA (§4) + fresh preflight snapshot SHA (this section) + authorized commit + episode/preset → the one production queue invocation.

**Rev6 — `snapshot_path`/`snapshot_sha256` are now mandatory, not merely compared-when-present.** Rev5 only compared these fields against the observed bytes *if the wrapper happened to report them*; a PASS whose JSON omitted either field passed the binding check by default. The published, hash-pinned wrapper's own `Rlce9901PreflightResult.to_dict()` deterministically includes both fields on every PASS, so their absence is itself contract-breaking evidence. `verify_fresh_preflight_snapshot_binding()` now requires `snapshot_path` to be a non-empty string (`fresh_preflight_snapshot_path_missing` otherwise) and `snapshot_sha256` to be a well-formed 64-character hex SHA-256 value (`fresh_preflight_snapshot_sha256_missing` otherwise) before comparing either against the independently-observed bytes.

`.exists()` returning `True` does not guarantee `.read_bytes()` will succeed — an independent replay reproduced an uncaught `IsADirectoryError`. The read is now wrapped and classified as its own distinct failure, `fresh_preflight_snapshot_unreadable`, alongside `fresh_preflight_snapshot_missing`, `fresh_preflight_snapshot_hash_mismatch`, and `fresh_preflight_snapshot_path_mismatch` — all four stop before production launch, write snapshot-binding failure evidence, write `final_result.json` and `sha256_manifest.json`, preserve fresh stdout/stderr, and never retry.

Any failure here stops with evidence preserved (`mutation_boundary_recheck.json`) and the production CLI is never launched.

**Rev3 Finding R3-5**: the actual second-pass proof is now preserved, not discarded. Rev2's `mutation_boundary_recheck.json` recorded only `{"result": "passed"}` on success; the function's own return value (source hashes, preflight-wrapper SHA, the full second DB baseline) was computed and then thrown away. ## 6. Full Resolve mutation surface a future authorization must cover

Unlike the getter-only preflight, a live queue attempt can legitimately cause the existing, unmodified production source to perform:

- Resolve connection (`ResolveScriptAdapter.connect()`, at process startup)
- `ProjectManager.LoadProject()` during the collision-inspection pass (`RenderManager._reject_collisions()` → `ResolveAdapter.list_render_jobs()`)
- `ProjectManager.LoadProject()` again during the renderability-inspection pass (`RenderManager._enforce_renderability()` → `ResolveAdapter.get_video_timeline_item_count()`)
- `ProjectManager.LoadProject()` a third time, plus `Project.SetCurrentTimeline()`, at the start of `ResolveAdapter.queue_render_job()`
- `Project.LoadRenderPreset("Redline Broadcast Master")`
- `Project.SetRenderSettings({...})`
- exactly one `Project.AddRenderJob()` call
- getter/reconciliation calls (`GetRenderJobList()` before and, if needed, after `AddRenderJob()`)
- only if existing production reconciliation requires it after a failure: one best-effort `Project.DeleteRenderJob()` (per `ResolveAdapter.delete_render_job()`, called from `RenderManager.queue_render()`'s own failure-handling branch)

`Project.StartRendering()` is **not** in this list. It does not appear anywhere in `resolve/adapter.py` and is not reachable from `queue_render_job()`, `list_render_jobs()`, `get_render_status()`, or `cancel_render()` (§11). A future founder authorization for a live queue attempt must explicitly cover this full surface — not just "`AddRenderJob()`" — because `LoadProject()`/`SetCurrentTimeline()` are real, already-existing production calls this pathway makes before `AddRenderJob()` is ever reached.

**Rev2 Finding 2 makes this stronger still**: Resolve connection itself (`ResolveScriptAdapter.connect()`) happens even earlier than any of the above — `runtime/composition.py`'s `build_application_services()` calls it unconditionally, before `render_commands.run()` is ever reached, which is itself before `RenderManager.queue_render()`'s very first check (episode lookup). Every item in this list, and every RenderManager failure mode described in §9, occurs after that connection — there is no code path through this pathway that contacts Resolve later than this or not at all, once the production process has started running Python.

## 9. Classification model — Rev2 corrected

Rev1's classification "A: failure before Resolve mutation" was imprecise in two independent ways, both corrected in Rev2. **Finding 2**: `runtime/composition.py`'s `build_application_services()` calls `resolve.connect()` unconditionally before `RenderManager` ever runs (§6), so no RenderManager-raised failure — including "episode not found" — can honestly be called "no Resolve contact". **Finding 3**: a falsy `LoadRenderPreset()`/`SetRenderSettings()` return does not prove no Resolve state changed, only that Redline did not confirm success. The harness now classifies every completed attempt into exactly one of:

1. `PRODUCTION_PROCESS_NOT_LAUNCHED` — reserved exclusively for an `OSError` that prevented the production process from starting at all. The only case this harness can actually prove made zero Resolve contact.
2. `PRODUCTION_TIMEOUT_RECONCILIATION_REQUIRED` — **(new, Rev3 Finding R3-7)** the production process was force-terminated after exceeding the timeout. Checked immediately after `PRODUCTION_PROCESS_NOT_LAUNCHED` and before any DB-state inspection, so a forced timeout can never classify as success merely because the partial DB state happens to look complete by coincidence — proven by three adversarial tests covering a `claiming` row, a fully row-matching `queued` state, and no new row at all, none of which pass.
3. `RESOLVE_CONNECTED_EARLY_FAILURE_NO_CLAIM` — a known RenderManager failure (episode/preset/config error, local filesystem/DB collision) occurring after Resolve connection but before any SQLite claim. *(Rev1 called this `NO_RESOLVE_CONTACT_YET` — removed; that name is no longer accurate for any live outcome.)*
4. `RESOLVE_STATE_SELECTION_NO_CLAIM` — `LoadProject()` is confirmed to have occurred (renderability check, live Resolve collision, or claim-race collision), still no successful SQLite claim.
5. `SQLITE_CLAIM_RENDER_CONFIGURATION_FAILED_BEFORE_ADD_ACCEPTANCE` — `LoadRenderPreset()`/`SetRenderSettings()` failed; either call may have been attempted against Resolve before failing. *(Rev1 called this `SQLITE_CLAIM_NO_SETTINGS_MUTATION` — renamed; that name overclaimed.)*
6. `SETTINGS_MUTATED_ADD_NOT_ACCEPTED` — `AddRenderJob()` returned `False`.
7. `ADD_CALLED_ACCEPTANCE_UNOBSERVED` — `AddRenderJob()` was called but queue acceptance is ambiguous/unresolved.
8. `PRODUCTION_QUEUE_PATH_ACCEPTED` — see the strengthened requirements below and the "Classification proof boundary" section. *(Rev1 called this `QUEUE_ACCEPTED_WITH_JOB_ID` and required far less evidence — renamed and strengthened in Rev2, strengthened again in Rev3.)*

10. `RECONCILIATION_ROLLBACK_FAILED_MANUAL_REQUIRED` — as above, but rollback itself failed; manual reconciliation required.
11. `UNCLASSIFIED_REQUIRES_REVIEW` — the fail-closed default whenever evidence does not match a known, sourced pattern. Never a guessed success or "safe" outcome. An independent replay reproduced both as real false-passes: raw `b"\xff"` stderr and a bare `b"\n"` both passed. Any nonzero raw byte count now fails closed, and the exact byte count is preserved in classification evidence (`stderr_byte_length`).
- **(Rev4 Finding 2; uniqueness strengthened Rev5)** production CLI stdout **must contain and agree on all eight** deterministic fields the hash-pinned CLI prints on success: `Job ID` (== the DB row's own `id`), `Episode ID` (== `RLC-E9901`), `Preset` (== `broadcast_master`), `Project` (== `RLC-E9901_MASTER`), `Timeline` (== `RLC-E9901_TIMELINE`), `Resolve Job ID` (== DB `resolve_job_id`), `Status` (== `queued`), `Output` (== the exact path) — plus the literal lines `Rendering started: no` and `Archive performed: no`. Rev3 required only three of the eight fields (`Resolve Job ID`/`Status`/`Output`) and treated the other five as merely "preferred"; an independent replay reproduced a false pass with stdout containing only that minimal three-field subset. All eight are now required present, not merely checked-if-present.

  **Rev5 — every label must occur exactly once; duplicates fail closed regardless of value agreement.** The Rev4 parser recorded only the *last* occurrence of each labelled field (a second `Job ID:` line silently overwrote the first) and reduced the two confirmation lines to a boolean "was the exact `...: no` string ever seen anywhere in the output" flag, which silently ignored a contradictory `...: yes` line printed elsewhere in the same stdout. An independent replay reproduced both as real false-passes: a wrong/fabricated block followed by (or preceded by) the genuine correct block, and `Rendering started: yes` alongside `Rendering started: no`, both still classified as `PRODUCTION_QUEUE_PATH_ACCEPTED`. The parser now preserves every occurrence of every label as a list, never collapsing repeated labels into one value (`first-value-wins` is exactly as disqualified as `last-value-wins`), and requires:
  - each of the eight deterministic fields to occur **exactly once** — zero occurrences fails closed (unchanged from Rev4), and **two or more occurrences fails closed even when every occurrence carries an identical value** — production source has no legitimate reason to print the same deterministic field twice, so a duplicate is itself treated as contradictory evidence, not confirmed evidence;
  - the `Rendering started:` confirmation family to occur **exactly once**, with that sole occurrence's value equal to `no` — any count other than exactly one (zero, two, or more) fails closed, and a lone occurrence whose value is anything other than `no` (e.g. `yes`) fails closed;
  - the `Archive performed:` confirmation family to occur **exactly once**, with that sole occurrence's value equal to `no`, under the identical rule.

  Classification evidence (`evidence["stdout_occurrences"]`) preserves the full per-label occurrence list, not a collapsed dictionary value, so any duplicate or contradictory evidence a reviewer needs to inspect remains visible rather than silently resolved one way or the other during classification.

Any single mismatch fails closed to `UNCLASSIFIED_REQUIRES_REVIEW`, never to a weaker "partial success".

**One documented residual ambiguity**: `RenderOutputCollisionError`'s category string ("render collision") is identical whether the collision came from a purely local filesystem/DB check or from a live Resolve render-queue comparison (`_reject_collisions()`'s loop over `resolve.list_render_jobs()`, which does call `LoadProject()`). The harness narrows this using its own immediately-prior filesystem/DB collision gate (§8) and a distinguishing detail in the exact exception text (a numeric job ID present only in the local-DB-collision message), but states the residual uncertainty explicitly in code comments rather than silently picking one.

### Classification proof boundary

**A successful mutation-harness result proves `PRODUCTION_QUEUE_PATH_ACCEPTED` — production queue-path acceptance according to the production CLI/adapter/SQLite evidence.** It does **not**, by itself, close final independent proof that the expected job exists in Resolve's own actual render queue. That final proof requires a later, separate, separately authorized read-only getter-only evidence-closure observation of Resolve's actual queue state — which this harness deliberately does not add. Mutation and independent evidence closure are kept as two distinct authorizations, not one.

## 11. `StartRendering()` boundary

Confirmed by direct source read: `Project.StartRendering()` does not appear anywhere in `src/redline_core/resolve/adapter.py`, and is therefore not reachable from `queue_render_job()`, `list_render_jobs()`, `get_render_status()`, or `cancel_render()`. A static test (`test_harness_source_contains_no_direct_resolve_scripting_api_calls`) additionally proves the harness's own source contains no `StartRendering(` call (nor `LoadRenderPreset(`/`SetRenderSettings(`/`AddRenderJob(`/`scriptapp(`/`DaVinciResolveScript` — the harness only ever launches the production CLI as an opaque subprocess).

**Rev4 Finding 5 — precision correction.** This harness does **not** independently observe Resolve's rendering or queue state at any point after the production queue attempt — it contacts Resolve at all only through the one fresh getter-only preflight subprocess, which runs *before* the production CLI, not after. What it *can* and does prove: from hash-pinned production source, that the production queue path contains no call to `StartRendering()` anywhere it could reach; and, as one of `PRODUCTION_QUEUE_PATH_ACCEPTED`'s own requirements (§9), that the expected Broadcast Master `.mov` file remains absent from disk immediately after the attempt. Neither of these is the same claim as "no rendering occurred" — a render could in principle be triggered manually, by a separate process, or by some other means this harness never contacts Resolve to observe. Actual post-attempt Resolve queue/rendering state is, and remains, the job of a subsequent, separately authorized, read-only getter-only evidence-closure observation (see the "Classification proof boundary" section) — this harness must never be read as implying it can detect arbitrary external or manual rendering activity it never observed in the first place.

## 12. Exactly-one queue semantics

Structurally enforced, not merely operator discipline — and, per **Rev2 Finding 9**, stated precisely rather than overclaimed. Rev1 claimed "exactly two `subprocess.run(...)` call sites in the entire module"; independent review found this false: an independent AST pass found **four** direct call sites — `_run_git()` and `verify_python_interpreter()` (non-Resolve infrastructure checks, callable from any safe construction-time subcommand) in addition to the two mutation-relevant ones, plus the dynamically-loaded module-provenance checker's own internal subprocess call. The actual, corrected invariant — proven by `test_exactly_one_production_cli_launch_site`, `test_exactly_one_fresh_preflight_launch_site`, and `test_all_subprocess_run_call_sites_are_known_and_accounted_for` (which enumerates and pins the complete four-site inventory) — is: exactly ONE code site can launch the mutation-bearing production CLI, reached at most once, no loop, no retry; exactly ONE code site launches the fresh getter-only preflight guard, same constraints; both live inside `run_authorized_queue_attempt()` (`test_no_loop_statement_wraps_run_authorized_queue_attempt_body`). The harness never calls `RenderManager`/`ResolveAdapter` directly at all (`test_harness_never_imports_render_manager_or_resolve_adapter`).

## 13. What this harness does not authorize or do

- Does not itself decide to queue, start, cancel, or delete a render.
- Does not perform any cleanup, repair, or second submission beyond what already-reviewed production code performs on its own.
- Does not modify the historical preflight evidence, the RLC-E9901 workspace, the runtime database (beyond what the one authorized production CLI invocation itself performs), or the repository.
- Construction of this file did not stage, commit, or push anything, execute the live getter-only preflight, or contact DaVinci Resolve.
