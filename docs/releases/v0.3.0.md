## Highlights

- First complete CLI transport (`redline` console script) for episode lifecycle, asset verification, and archive management, sharing one composition root with the MCP server.
- Timeline naming centralized to a single owner — `TimelineBuilder.timeline_name_for_episode()` — removing a pre-existing duplication between `TimelineBuilder` and `EpisodeManager` (Mission 11A).
- CLI now covers every public `TimelineBuilder` method except `apply_markers()` (deliberately excluded — no natural episode-scoped argument shape; see `docs/ARCHITECTURE.md` §5.1).
- Three composition tiers (`ApplicationServices`, `CoreServices`, `PersistenceServices`), each added only when a real command demonstrated that specific dependency boundary.

## Architecture

- `TimelineBuilder` owns timeline naming; no transport (CLI or MCP) re-derives `config.timeline.timeline_name_pattern` itself.
- The Resolve adapter owns all Resolve API contact; no other module touches raw Resolve objects.
- Managers own orchestration; both CLI and MCP are thin transports with no business logic of their own — verified during the Phase 3 audit that neither transport duplicates or second-guesses a manager decision.
- Dependency direction is clean: `redline_core` imports neither `cli` nor `mcp_server`; `cli` imports neither `mcp_server` nor the reverse.

## Resolve Integration

- Timeline creation is idempotent: an existing timeline is reused by exact name, never duplicated.
- Marker application is append-only: no deduplication at any layer — calling `build-timeline` twice against the same episode duplicates markers on the timeline (each call reports `markers_applied == N`, but the timeline ends up with `2N` markers).
- Clip placement is append-only: no deduplication at any layer — calling `place-clips` twice with the same clip IDs places them twice.
- No automatic rollback anywhere in the Resolve-touching path; no hidden retries. All of the above is documented `TimelineBuilder`/`ResolveAdapter` behavior, not a CLI defect, and no CLI command compensates for it.

## Composition

- `ApplicationServices` — full runtime: config + SQLite + Resolve + all six managers.
- `CoreServices` — configuration-only, no SQLite, no Resolve (`AssetManager`).
- `PersistenceServices` — configuration + SQLite, no Resolve (`ArchiveManager`).

Each tier's three public builders share small private construction helpers (`_resolve_config_dir`, `_resolve_db_path`, `_connect_database`) without merging their own public behavior.

## Known Limitations

- No rollback, no cross-process concurrency guard, and no duplicate-detection at any Resolve-touching layer. These are pre-existing, documented Phase 1/2 characteristics, not introduced in Phase 3.
- The MCP tool surface does not expose `place_clips` or `build_episode`/episode assembly — CLI capability currently exceeds MCP capability for these two operations. This is a known, documented asymmetry, not a defect; nothing requires transport parity, but it should be a deliberate consideration if Phase 4 work touches the MCP layer.
- `mcp_server/tools/media_tools.py`'s `organize_bins` tool and `mcp_server/tools/timeline_tools.py`'s `build_timeline`/`add_markers` tools have no exception handling at the MCP-tool layer at all (pre-existing, predates Phase 3, already documented in `docs/ARCHITECTURE.md`).
- Minor cosmetic inconsistency in CLI result-printer label alignment across `episode`/`archive` actions (does not affect exit codes, result payloads, or any test assertion — cosmetic only).
